# 共享翻译核心：职责、契约与演进

状态：2026-09-05 明确的项目架构方向。本文同时记录已实现能力与待实现契约；“目标契约”和迁移阶段不是当前 API 的完成声明。本轮只明确文档，不改运行代码，不启动代理盲评。

## 定位与文档分工

CueWeave 由浏览器扩展、桌面应用和共享翻译核心组成。算法、提示词、通用校验与质量评测属于共享核心的演进，而不是扩展专属功能。`@cueweave/core` 是在各宿主中运行的本地 TypeScript 库；这里的“基础设施”不意味着新增官方翻译服务器、独立常驻服务或对外发布 SDK。

- 本文维护两端共用的能力边界、目标契约、接入状态和迁移验收。
- [仓库结构](WORKSPACE.md)维护物理目录与依赖方向。
- [系统架构](ARCHITECTURE.md)维护系统关系与扩展运行上下文；[桌面规格](DESKTOP.md)维护桌面进程、媒体和项目要求。
- [翻译策略](TRANSLATION-STRATEGY.md)维护当前算法、三档预算、提示词行为和实测限制。
- [评测规范](EVALUATION.md)维护样本、参考、评审和复现方法；[路线图](ROADMAP.md)维护交付阶段。

## 职责边界

| 层             | 负责                                                                                                                    | 留给其他层                                                                 |
| -------------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 共享核心       | 规范化翻译输入；上下文预算；语义规划；提示词与 Schema；三档策略；输出证据和覆盖校验；有界恢复与复核；可序列化结果及诊断 | 不读取浏览器状态、媒体文件、数据库或凭据仓库；不依赖 Electron、WXT 或 DOM  |
| 扩展适配与应用 | YouTube 轨道获取；时间来源转换；Provider 域名权限；播放器当前位置与预取；消息会话；IndexedDB；页面字幕显示与操作        | 不自行维护另一份通用翻译提示词、三档定义或语义校验                         |
| 桌面适配与应用 | 媒体/字幕导入与 ASR 接入；时间来源转换；安全凭据；后台任务与 IPC；项目数据库；人工编辑、撤销和导出权限                  | 不为同一能力复制扩展或核心的翻译流程；不把人工修订保护下放为核心数据库逻辑 |
| 评测工具       | 固定样本、参考与评分规则；调用核心真实入口；匿名候选、证据评审、版本对照与质量/等待报告                                 | 不维护只在评测时使用的“更好提示词”；参考答案不进入翻译请求                 |

允许平台适配器限制请求域名、响应大小和资源使用，通过 `ProviderRuntime` 等注入。核心负责阶段预算、恢复策略和通用错误；宿主负责任务总预算、并发容量、调度、存储及用户取消。多层预算必须可追踪，避免宿主外层重试再叠加核心重试而无限放大成本。

## 同一核心，保留不同的时间约束

质量档位、分段方式与运行场景是三个独立维度，不能用一个档位隐含决定全部行为。

| 维度     | 目标表达                            | 约束                                                            |
| -------- | ----------------------------------- | --------------------------------------------------------------- |
| 质量预算 | `speed` / `balanced` / `quality`    | 统一命名与语义目标；恢复、上下文与复核预算由核心策略集中定义    |
| 分段方式 | `preserve-cues` / `semantic-reflow` | 前者固定 ID、顺序和时间；后者仅在时间证据允许时重组连续来源范围 |
| 调度场景 | 跟播 / 完整项目 / 批量任务          | 由宿主决定优先级和持久生命周期；核心接收有界任务及取消信号      |

上述分段方式名称是目标契约，不是已经导出的类型。

- **保留 cue**：SRT、WebVTT 或只有段级时间的 ASR 字幕可以使用完整上下文翻译，但输出必须保留原条目 ID、顺序和时间范围。不要求模型杜撰词级切点；也不能强制套用为英中重组字幕设计的去分句标点规则。
- **语义重组**：输入需携带词元及其时间依据。模型可以选择连续原文范围，本地生成时间；禁止模型生成新时间戳。精确词级时间、插值估算时间和未知时间质量必须可区分。缺少可靠时间依据时应保留 cue，或明确采用并标记经过单独验收的估算显示策略，不能伪装成词对齐。
- **时间证据**：当前 `SourceToken` 只有时间值，没有完整表达时间质量；目标输入须补充时间粒度与来源。现有扩展可能使用分段偏移和插值，这是迁移时需要显式保留的事实，不能简单给旧输入统一贴“可靠词级时间”标签。
- **语言能力**：当前三档重组提示词以英文到简体中文为主。桌面 cue 路径的多目标语言不代表核心所有语言都支持同样的分段和实体规则。支持矩阵应由核心声明；不支持的组合返回明确结果，不能静默使用不适用的中文规则。

两端可以选择不同分段方式和调度场景，但应共享同一套质量预算定义、原文证据原则与评测口径。共享不要求两端具有相同的界面、窗口数量或毫秒延迟。

## 目标调用契约（待实现）

目标是在现有领域和传输能力上增加一个窄的翻译任务入口，先服务仓库内部的两个应用与评测，不提前承诺外部 SDK 兼容性。具体函数名称在实施时确定，不在本文虚构可调用 API。

**输入**应包含：原始内容与稳定来源 ID、输入修订/摘要、源语言和目标语言、时间粒度与证据、分段方式、质量档位、受限上下文、已确认术语和纠词许可。平台标题等属于可选上下文，不要求每个任务有 YouTube 视频 ID。宿主注入 Provider 访问、取消及诊断能力；密钥不进入任务指纹、持久结果或日志。

**输出**应区分：已校验的可用字幕、未完成来源范围、原始转录与应用修正、自动术语建议、处理阶段与警告、实际使用的策略/提示词/Schema 版本。完整、部分完成、失败和取消要有明确语义；复核状态单列，“复核通过”只说明流程与校验通过，不代表人工质量认证。

**生命周期**应支持：阶段进度、可用局部结果和最终结果，取消后不再接受新结果，恢复只处理仍然缺失的范围。当前返回值和诊断回调只覆盖其中一部分，不是已实现的完整事件协议。是否先显示初稿再异步修订，应另行验证跟播稳定性，不默认改变当前用户看到的字幕。

**上下文与修订**应保持可追踪。任务结果携带其输入修订；宿主在写入前核对项目/轨道/会话及人工编辑修订。过期结果即使翻译正确也不得覆盖新内容。核心不拥有项目锁、数据库事务或撤销栈。

**缓存与检查点**分开处理：缓存用于复用等价已完成结果；检查点用于恢复未完成任务。核心应给出可复用的版本指纹/校验契约，宿主决定存储介质、容量和淘汰。身份至少区分输入、语言、Provider/模型/协议、分段方式、档位、策略/提示词/Schema 版本、纠词许可和影响输出的固定上下文/人工术语。动态前文采用明确的上下文快照及恢复校验规则，不能盲目把全部历史塞入键，也不能忽略上下文变化而复用不等价结果。现有两端存储无需统一成同一种数据库。

## 算法、提示词与质量的共同管理

算法和提示词作为同一可版本化的处理策略发布。通用忠实性原则、原文归属规则、错误分类与恢复语义集中在核心；分段和语言的专用约束通过明确的处理配置组合，不在宿主复制整段 prompt。当前 `translationPolicy.ts`、`subtitlePrompt.ts` 与 `firstPass.ts` 是词元路径的起点，而非所有路径已经统一的完成证明。

速度、均衡与质量使用相同的质量衡量标准。质量分、严重错误、完整性、显示对应、首次可用、长尾等待和请求成本分别报告，不能用完整覆盖代替语义正确，也不能用快速响应抵消否定翻反。评分权重和通过阈值需先校准，之前的主观百分制估分不作为发布门槛。

代理盲评可以作为离线评测的一种评审来源：隐藏档位和耗时、冻结标准、逐问题附证据、独立评审后记录分歧。它不等同于独立人工或真实观看验收。当前先完成项目边界整理，后续另行启动盲评，不在产品翻译过程中自动增加裁判调用。

## 迁移顺序与完成条件

1. **冻结边界与基线。** 本文明确职责；保留现有三档输出、代码和提示词快照。完成条件是可准确说明每端使用了哪条流程，不把待实现契约写成能力承诺。
2. **收敛固定 cue 能力。** 将桌面通用分窗、提示词、解析和恢复移到核心的固定 cue 路径，桌面保留安全传输适配、项目和任务生命周期；先用保存响应和固定回归输入确认迁移没有暗中改变含义、顺序和时间。迁移不等于此时强制启用语义重组。
3. **统一任务与策略契约。** 两种分段方式共用明确的档位、取消、局部结果、版本指纹与诊断语义；扩展迁移到同一门面。检查点恢复须验证输入、上下文和版本，人工编辑保护由宿主验收。
4. **建立共享质量基线。** 统一评分标准后评审两种分段方式、三档与已声明语言组合；加入未参与调试的视频并重复运行。模型/策略升级记录质量收益、严重错误和等待成本，再决定是否采用，不能只挑最好的一次输出。
5. **跨端验收。** 同一规范化输入、配置及录制 Provider 响应，在扩展适配、桌面适配和评测入口产生等价核心结果；另分别验证扩展跳转/后台回收，以及桌面取消/崩溃恢复/人工编辑保护。真实模型输出有随机性，不能要求不同时间运行的文本字节相同。

本轮完成的是第 1 步的文档边界，不包含后续代码迁移、评分执行或桌面功能验收。后续新增翻译能力先确定归属；只有平台生命周期和输入/输出适配留在应用层，避免形成三份互相漂移的翻译实现。
