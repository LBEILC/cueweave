# 流媒体翻译目标与策略

用户于 2026-09-05 明确：字幕应及时出现、意思清楚、持续跟上播放。质量与速度必须一起评估，不为最后少量润色增加数倍等待。可以重构窗口算法或整个 prompt；现有实现不是必须保留的约束。

## 当前实现

生产默认仍为 `balanced`；`speed` 是共享核心和基准 CLI 中可选的实验策略，尚未加入桌面或扩展的设置界面。不要把完成实验等同于已发布用户档位。

| 策略     | 请求窗口                                                 | 首轮提示词                   | 最多恢复阶段调用 | 每阶段瞬时网络错误重试 |
| -------- | -------------------------------------------------------- | ---------------------------- | ---------------: | ---------------------: |
| speed    | 本地窗口；附近句末标点、停顿的低成本接缝调整；带相邻原文 | 精简规则、一次输入词元与时间 |                1 |                      0 |
| balanced | 模型滚动接缝规划，失败使用本地边界                       | 原有完整规则与首轮检查指引   |                2 |                      1 |

两种策略共用结构、范围、实体证据和数字尺寸校验，不强制增加模型复核。恢复只由不可用输出触发，不因措辞不够漂亮阻断。阶段调用预算不等于 HTTP 调用上限：自动协议回退和网络重试仍受传输层控制。现有单请求超时为 45 秒，当前没有把窗口总耗时宣称为硬 SLA。

尺寸先按数字处理，允许 `28x28`、`28×28`、`28乘28` 等价表示；尺寸改变或遗漏仍被拒绝，GPT-5.6、X28 等真正标识符继续做实体检查。

局部失败通过 `PartialTranslationError` 保留有效字幕和缺失词元。扩展播放端显示有效字幕，但窗口保持未完成且不缓存为完整结果。重试时从已接受词元计算连续缺失范围，不拼接不相邻的原文，也不重新请求成功部分。基准工具同样记录部分成功，防止因上层抛错低估实际交付。

实验调用需要一致地选择模式：`PlaybackPlan(tokens, saved, mode)`、`createSubtitleJsonRequest(..., mode)` 与翻译上下文 `translationMode`。以后接入设置时，必须把模式与策略版本加入窗口计划及译文缓存身份，防止两档混用旧结果。

## 本轮验证与取舍

三段 smoke 输入、相同 gemini-3.5-flash-lite、同版源码，按 speed / balanced / balanced / speed 顺序各重复两轮。六次片段运行每档全部完整产出；这只表示范围完整，不是语义质量分数。

| 片段     | 速度首次可用 / 总耗时（中位秒） | 均衡首次可用 / 总耗时（中位秒） |
| -------- | ------------------------------: | ------------------------------: |
| 访谈     |                     3.13 / 5.46 |                    9.32 / 12.03 |
| 日常对话 |                     2.31 / 7.95 |                    4.28 / 12.19 |
| 科普     |                     2.78 / 7.50 |                     3.72 / 9.93 |

离线串行流程包含规划与翻译，不模拟播放器并发、缓存、网络抖动下的缓冲或用户实际等待。样本只有三段，两次重复；访谈均衡第二轮存在较慢响应，中位数仍受其影响。初版 speed 科普单请求也出现约 12.7 秒延迟，因此不能承诺固定倍数加速。

对四份输出做原文对照检查：本地接缝调整后，初版 `I was gonna / say that` 的跨窗断裂不再出现；但 speed 仍存在单条范围错位、重复含义和中文语序问题。balanced 也有首支疫苗信息漏译、跨条重复、把“在家吃海鲜”改成“在家做海鲜”的问题。没有足够证据把任一模式称为质量达标或人工金标准。

本轮选择：先交付误拦截修复、有效字幕保留与局部重试；速度策略保留为可重复实验，不直接替换生产默认。不增加全窗二次审校。后续优先验证复杂条件句、未见过的视频、真实跟播缓冲与首屏等待，再决定默认策略及是否开放用户档位。

## 可复现评测

```powershell
node --import tsx scripts/run-translation-benchmark.ts --out .eval/benchmarks/speed-new --group smoke --mode speed --token-file C:/Users/LBLC/.v3-llm-token
node --import tsx scripts/run-translation-benchmark.ts --out .eval/benchmarks/balanced-new --group smoke --mode balanced --token-file C:/Users/LBLC/.v3-llm-token
node --import tsx scripts/compare-translation-strategies.ts --out .eval/benchmarks/comparison/REPORT.md .eval/benchmarks/speed-new .eval/benchmarks/balanced-new
```

先用 `--dry-run` 校验输入，不读取密钥或发请求。比较器拒绝输入、模型、策略版本或核心源码不同的运行；输出首次可用、整段耗时、请求数与缺失量。语义检查单独完成，不让参考译文进入模型输入。原始字幕、响应、用量与本地报告放在被 Git 忽略的 `.fixtures/` 和 `.eval/` 中。

本轮四份结果为 `.eval/benchmarks/tradeoff-{speed,balanced}-v2-{a,b}`，汇总在 `.eval/benchmarks/tradeoff-comparison/REPORT.md`。运行各自存有当时源码快照；最终随后补充尺寸守恒校验与扩展错误类型转发，不影响上述三段无尺寸输入的翻译请求。
